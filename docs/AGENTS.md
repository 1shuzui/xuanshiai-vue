# 宣誓爱项目 — 强约束规则文件

> **文件作用：** 项目级强约束，防止后续对话和开发偏离设计方向、擅自修改关键配置  
> **约束范围：** 所有 AI 助手、开发者、协作者  
> **优先级：** 最高（覆盖任何临时指令）  
> **更新日期：** 2026-07-20

---

## 🚨 核心约束（任何情况下不可违反）

### 1. 设计规范强锁定

- ✅ **所有前端代码必须严格遵循 `DESIGN.md` 的设计 Token**
  - 色彩：必须使用 `--canvas`, `--accent`, `--ink` 等定义的 CSS 变量
  - 字体：标题用 `--serif`，正文用 `--sans`
  - 圆角：严格按照 4px / 8px / 12px / 999px 等级使用
  - 间距：采用 8px 基础网格
  - 阴影：必须使用 OKLCH 暖色阴影，禁用纯黑阴影

- ❌ **禁止擅自修改设计规范**
  - 不得引入新的色彩变量（除非经过设计评审）
  - 不得修改 `DESIGN.md` 中的核心 Token
  - 不得使用纯黑 `#000` 或纯白 `#fff`
  - 不得使用高饱和冷色、婚庆红金色

### 2. 产品定位强锁定

- ✅ **所有功能必须符合 `PRODUCT.md` 定义的产品本质**
  - 认真婚恋，而非泛娱乐社交
  - 真实认证，而非虚假资料横行
  - 双向尊重，而非单向骚扰

- ❌ **禁止引入与产品定位冲突的功能**
  - 不做快速滑动匹配（类 Tinder）
  - 不做即时聊天（必须先申请认识）
  - 不做娱乐化、低俗化内容
  - 不做不透明的付费陷阱

### 3. 技术架构强锁定

- ❌ **禁止擅自修改以下核心配置**
  - `xuanshiai-vue/manifest.json` — UniApp 应用配置
  - `xuanshiai-vue/pages.json` — 路由与 Tab 配置
  - UniCloud 云函数与数据库结构（未经确认）
  - XMind 文件（`.xmind` 文件为产品需求源文件，禁止修改）

- ✅ **允许的技术操作**
  - 创建新页面（在 `pages/` 目录下）
  - 创建新组件（在 `components/` 目录下）
  - 修改页面内的 Vue 组件逻辑
  - 添加工具函数（在 `utils/` 目录下）

### 4. 文档更新强约束

- ✅ **任何重大变更必须先更新文档**
  - 产品定位变更 → 更新 `PRODUCT.md`
  - 设计规范变更 → 更新 `DESIGN.md`
  - 技术架构变更 → 更新 `README.md` 或项目文档

- ❌ **禁止未经文档确认的口头变更**
  - 对话中提到"改一下配色"→ 必须先确认是否符合设计规范
  - 对话中提到"加一个功能"→ 必须先确认是否符合产品定位

## 📐 前端开发约束

### 1. 设计一致性

- ✅ **新增页面/组件必须使用已有设计 Token**
  - 从 `DESIGN.md` 中复用色彩、字体、间距、圆角
  - 从高保真原型（`design-demos/final/`）中提取组件样式
  - 保持视觉语言一致（暖色调、大圆角、柔和阴影）

- ❌ **禁止引入新的设计风格**
  - 不得使用冷色调（除深暖蓝 `--navy` 用于 AI 功能）
  - 不得使用锐角、生硬边框
  - 不得使用纯色渐变背景（除特定功能卡片）

### 2. 组件复用

- ✅ **优先复用已有组件**
  - 按钮 → 从原型中提取的 `.primary` / `.secondary` / `.text-btn`
  - 卡片 → `.card` / `.grid-card` / `.feature`
  - 弹窗 → `.overlay` + `.sheet` / `.modal`
  - 输入框 → `.inline-input` / `.search`

- ❌ **禁止重复造轮子**
  - 不得自己写新的按钮样式（除非原型中不存在）
  - 不得自己设计新的卡片样式（除非产品需求明确）

### 3. 响应式设计

- ✅ **所有页面必须支持移动端**
  - 最小宽度 320px（小屏手机）
  - 标准宽度 375px / 390px（iPhone）
  - 最大宽度 428px（iPhone Pro Max）

- ✅ **浏览器开发模式（桌面预览）**
  - 1440×900 画布展示移动端原型
  - 居中显示 390×844 移动端界面

### 4. 性能优化

- ✅ **图片优化**
  - 使用 WebP 格式（兼容 JPEG 降级）
  - 压缩率 70—80%
  - 懒加载（超出可视区域的图片）

- ✅ **代码优化**
  - CSS 使用 CSS 变量，避免重复定义
  - JS 避免全局变量污染
  - 组件按需加载

## 🔒 产品功能约束

### 1. 会员权益透明化

- ✅ **必须清晰展示会员权益**
  - 列出所有权益对比（普通用户 vs 会员）
  - 明确付费金额与周期
  - 不使用"限时优惠"等诱导文案

- ❌ **禁止模糊付费逻辑**
  - 不得隐藏会员价格
  - 不得在用户不知情的情况下扣费
  - 不得使用"连续包月"默认勾选

### 2. 认证体系严肃性

- ✅ **认证结果必须真实展示**
  - 四类认证（实名/学历/头像/单身）
  - 认证状态明确标注
  - 认证说明透明展示

- ❌ **禁止虚假认证**
  - 不得允许用户上传他人照片
  - 不得允许虚假学历/职业信息
  - 不得允许已婚用户标注单身

### 3. 安全与隐私

- ✅ **必须保护用户隐私**
  - 举报功能易于触达
  - 安全提示前置展示
  - 用户可随时删除个人数据

- ❌ **禁止泄露用户隐私**
  - 不得向第三方售卖用户数据
  - 不得在未经同意的情况下展示用户联系方式
  - 不得记录用户敏感对话内容

## 🛠️ 技术操作约束

### 1. 文件操作权限

#### ✅ 允许的操作

| 操作 | 路径 | 说明 |
|------|------|------|
| 创建页面 | `xuanshiai-vue/pages/` | 新增功能页面 |
| 创建组件 | `xuanshiai-vue/components/` | 可复用组件 |
| 修改页面 | `xuanshiai-vue/pages/**/*.uvue` | 页面逻辑与样式 |
| 创建工具函数 | `xuanshiai-vue/utils/` | 辅助函数 |
| 修改全局样式 | `xuanshiai-vue/uni.scss` | 设计 Token（需确认） |
| 创建文档 | 根目录 `.md` 文件 | 项目文档 |

#### ❌ 禁止的操作

| 操作 | 路径 | 原因 |
|------|------|------|
| 修改应用配置 | `xuanshiai-vue/manifest.json` | 核心配置，需团队确认 |
| 修改路由配置 | `xuanshiai-vue/pages.json` | Tab 结构已固定 |
| 修改 UniCloud | `xuanshiai-vue/uniCloud-aliyun/` | 后端逻辑，需后端确认 |
| 修改 XMind | `*.xmind` | 产品需求源文件，禁止修改 |
| 删除高保真原型 | `design-demos/final/` | 设计参考文件 |
| 修改项目规则 | `PRODUCT.md` / `DESIGN.md` / `AGENTS.md` | 需团队评审 |

### 2. Git 操作约束

- ✅ **允许的操作**
  - 创建新分支（`feature/xxx` / `fix/xxx`）
  - 提交代码到自己的分支
  - 合并到 `dev` 分支（经过测试）

- ❌ **禁止的操作**
  - 直接推送到 `main` / `master` 分支
  - 强制推送（`git push -f`）
  - 删除他人的分支
  - 修改已发布的 Tag

### 3. 依赖管理约束

- ✅ **允许的操作**
  - 安装必要的 npm 包（需说明用途）
  - 更新小版本依赖（`1.2.3` → `1.2.4`）

- ❌ **禁止的操作**
  - 安装未经确认的第三方库
  - 更新大版本依赖（`1.x.x` → `2.x.x`）
  - 删除已有依赖

## 🗣️ 对话协作约束

### 1. AI 助手行为约束

#### ✅ 允许的行为

1. **回答技术问题**
   - 解释代码逻辑
   - 提供实现方案
   - 调试错误

2. **实现已确认的功能**
   - 按照 `PRODUCT.md` 和 `DESIGN.md` 实现
   - 复用已有组件和样式
   - 保持设计一致性

3. **建议优化方案**
   - 提出性能优化建议
   - 提出用户体验改进建议
   - 提出代码重构建议

#### ❌ 禁止的行为

1. **擅自修改核心配置**
   - 不得未经确认修改 `manifest.json`
   - 不得未经确认修改 `pages.json`
   - 不得未经确认修改 UniCloud 配置

2. **偏离设计规范**
   - 不得使用 `DESIGN.md` 之外的颜色
   - 不得引入新的字体
   - 不得破坏视觉一致性

3. **偏离产品定位**
   - 不得建议娱乐化功能
   - 不得建议降低认证门槛
   - 不得建议不透明的付费逻辑

4. **给出错误建议**
   - 不得说"可以暂时用纯黑色"（违反设计规范）
   - 不得说"可以跳过认证"（违反产品定位）
   - 不得说"可以先不管安全"（违反安全要求）

### 2. 用户请求处理规则

#### 当用户请求与约束冲突时

**正确做法：**
```
用户：把主色改成亮蓝色
AI：宝宝 😊，根据 DESIGN.md 的设计规范，宣誓爱的主色是低饱和青瓷绿（--accent），
    不使用高饱和冷色。如果需要调整主色，建议先在 DESIGN.md 中评审并更新设计 Token。
    
    要不要我先帮你看看为什么想改成亮蓝色？是不是有其他设计目标？
```

**错误做法：**
```
用户：把主色改成亮蓝色
AI：好的，我帮你把主色改成 #0080ff
```

#### 当用户请求不明确时

**正确做法：**
```
用户：加个按钮
AI：宝宝 💕，想加什么样的按钮呢？
    - 主按钮（深暖棕背景，用于核心操作）
    - 次要按钮（浅色背景 + 边框）
    - 文字按钮（透明背景）
    
    按钮放在哪个位置？做什么功能？
```

**错误做法：**
```
用户：加个按钮
AI：好的，我加了一个蓝色按钮
```

## 🆘 异常情况处理

### 1. 设计规范与需求冲突

**场景：** 用户要求的功能与设计规范冲突

**处理流程：**
1. 说明冲突点
2. 提供符合规范的替代方案
3. 如果用户坚持，建议先更新 `DESIGN.md`
4. 等待团队评审

### 2. 产品定位与需求冲突

**场景：** 用户要求的功能与产品定位冲突

**处理流程：**
1. 说明冲突点（参考 `PRODUCT.md`）
2. 解释为什么不适合宣誓爱
3. 提供符合产品定位的替代方案
4. 如果用户坚持，建议先更新 `PRODUCT.md`

### 3. 技术限制

**场景：** UniApp 不支持某些 Web 特性

**处理流程：**
1. 说明技术限制
2. 提供 UniApp 原生替代方案
3. 如果无法替代，提供降级方案
